# DCMS M1.3 — Charger Details, Editing, QR, and Photos

## User flow
1. Dashboard -> Charger Inventory -> select a charger.
2. Detail shows permanent asset code, model, nominal ratings, QR identity, and photo gallery.
3. Edit Data Charger modifies information without changing UUID or asset code.
4. Tambah Foto -> Kamera or Galeri -> copies a selected image into the app documents directory.
5. Inventory -> Scan icon -> scans a DCMS QR and looks up the matching charger in local SQLite.

## QR payload
Format: `dcms:charger:<UUID>`.
- Asset labels visibly show `CHG-0001` etc., while QR encodes immutable UUID.
- Scanner recognizes only DCMS QR payloads and checks that the referenced charger exists in the local database.
- Generating a visible QR is implemented. Export/printing of QR labels is **not implemented** yet.
- No cloud lookup is performed.

## Photos
- Powered by `image_picker`, stored in the application's private documents directory:
  `charger_photos/<charger_uuid>/<photo_uuid>.<extension>`
- SQLite `charger_photos` table stores relative paths and metadata only.
- Supports camera and gallery, one image per selection; repeat to attach multiple photos.
- Picker requests maximum dimensions of 1600 × 1600 and quality 82; max stored file size 10 MiB per photo.
- Photo records generate a `photo_added` event.
- App uninstall or clearing app data may delete photos. **Local backup/restore, export, photo deletion, and photo recovery after Android process termination are still pending.**
- Do not put genuine workshop photos or customer records in the public GitHub repository.

## Migration
SQLite schema upgraded v2 -> v3 by adding `charger_photos` and index; other existing charger records are preserved. Always back up existing pilot data before experimenting with schema changes when a reliable backup option exists.

## Privacy/security before company-data pilot
Android may automatically back up application data depending on device/OS settings and AndroidManifest configuration. Before using any real company/customer data:
1. Confirm company permission and phone storage/access policy.
2. Generate Android platform files and review `android/app/src/main/AndroidManifest.xml`.
3. Set `android:allowBackup="false"` on the `<application>` element and review Android 12+ data-extraction rules to prevent unwanted cloud backup or device transfer; test behavior on intended Android versions.
4. Complete reliable local backup/restore of BOTH SQLite database and image directory.
5. Do not share private app files via GitHub or other public channels.

## Local verification (Flutter SDK needed)
```powershell
git pull origin main
flutter create --platforms=android .
flutter pub get
flutter analyze
flutter run
```
If Android platform files already exist, do not overwrite customized files without reviewing changes.

The `mobile_scanner` 6.0.x plugin requires Android `compileSdk` at least 34. Ensure your Android toolchain/Gradle settings satisfy it.

### Smoke tests
- Create two chargers and verify distinct `CHG-0001` / `CHG-0002` IDs.
- Open detail; QR displayed and stable.
- Edit brand/serial/nominal ratings and confirm original QR/asset code unchanged.
- Upload a gallery image and capture a camera image; verify both appear.
- Restart the app and confirm data/photos remain.
- Scan the QR on another screen and verify it opens the correct charger.
- Invalid/unregistered QR must not open an unrelated charger.
- For an existing v2 pilot DB, migration to v3 should preserve all charger records.

## Known limitations
- No Flutter analyzer/build/device tests have been performed by the assistant.
- Single device SQLite; not a synced multi-user solution.
- Owner/location selection, QR print/export, backup/restore, and audit operator authentication remain later M1 tasks.
